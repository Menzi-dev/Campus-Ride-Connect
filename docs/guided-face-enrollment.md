# Guided face enrollment

Web registration now uses MediaPipe Face Landmarker to inspect a live camera
stream. It requires exactly one face, a usable frame size, a forward-facing
calibration, two head turns in randomized order, a blink with open eyes before
and after, and a final forward-facing hold. Images are captured automatically
only after the sequence. Permission, model-loading, tracking, and timeout
failures allow retry. Camera tracks stop when scanning finishes or the screen
unmounts. Native registration currently directs users to the HTTPS web app.

The detector and model load from pinned-version jsDelivr and Google's model
hosting. Face processing occurs in the browser; these hosts receive asset
requests, not camera frames. Enrollment requires consent and uploads one JPEG
plus completion metadata with registration. The server stores the JPEG in
`users.face_enrollment_photo` (LONGTEXT), and client-reported completion details
in `users.face_scan_metadata` (TEXT). Both fields are excluded from account JSON.
The existing development JPA schema update creates these columns at restart;
production needs a reviewed schema migration.

This is a local guided movement check, not anti-spoofing or identity matching.
A malicious client can fabricate a completion result. `face_verified` remains
false, and legacy photo-only verification endpoints return HTTP 410. No face
embedding is generated by this implementation. A future server-validated
liveness service must be integrated before treating these accounts as verified.

Physical-device acceptance: try no face, two faces, incorrect turns, only closed
eyes, a correct complete sequence, camera denial, back navigation during scan,
retry, and enrollment submission. Check stored metadata and confirm account
responses do not include the enrollment image. A prerecorded video may pass;
the feature must not be presented as spoof-resistant.
